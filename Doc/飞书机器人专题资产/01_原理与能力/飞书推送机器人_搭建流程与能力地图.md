# 飞书推送机器人 · 搭建流程与能力地图

> 用途:把"搭建一个飞书内部推送机器人"这件事拆解为流程、接口与能力清单,用于判断自身能力缺口、制定学习计划,并归档进职业资产档案。
> 场景:企业自建应用机器人,面向公司内部员工推送消息(文本 / 富文本 / 图片 / 语音 / 视频 / 消息卡片),消息直接落在飞书聊天列表,无需点开订阅号查看。
> 整理日期:2026-08-04

---

## 一、先理清:两种飞书机器人的区别

飞书有两种"机器人",能力差别很大,选错方向会白学:

| 类型 | 怎么创建 | 能发的消息 | 是否是本方案 |
|---|---|---|---|
| **自定义机器人(群 webhook)** | 群设置里"添加机器人",拿一个 webhook 地址 | 文本、富文本、图片、消息卡片、群名片 | ❌ 发不了语音/视频,只能发到所在群 |
| **企业自建应用机器人** | 飞书开放平台创建应用,开启机器人能力 | 文本、富文本、图片、**语音**、**视频**、文件、消息卡片 全支持 | ✅ 本方案 |

关键判断依据:**能发语音和视频的,一定是自建应用机器人**。它在飞书里是一个独立会话联系人,推送就像同事发消息一样直接亮在聊天列表。

## 二、完整搭建流程(五步)

```
建应用 → 配权限 → 换 token → 上传素材 → 调接口发消息
（平台配置）        （后端开发核心）
```

### 步骤 1 · 创建应用(平台配置,不写代码)
- 在[飞书开放平台](https://open.feishu.cn)创建「企业自建应用」。
- 拿到应用的 **App ID** 和 **App Secret**(后端鉴权的凭证,相当于账号密码,需妥善保管)。
- 开启「机器人」能力。
- 把应用**发布上线**——内部应用需走企业的发布 / 审核流程(通常由企业管理员或应用管理员审批)。

### 步骤 2 · 配置权限与可见范围(平台配置)
- 在应用后台开通发消息相关权限,核心是 **`im:message`**(以应用身份发消息);按需要再加获取用户信息、获取群信息等权限。
- 配置**可见范围**:决定这个机器人能推给哪些人 / 哪些部门。给谁发,就要有对应的接收范围。

### 步骤 3 · 获取访问凭证 token(后端开发)
- 后端用 App ID + App Secret 调接口换取 **`tenant_access_token`**(企业自建应用用这个)。
- 注意:token **有效期约 2 小时**,必须自己做**缓存 + 到期自动刷新**,不能每次都重新申请(会触发频率限制)。
- 之后每次调发消息接口,都在请求头带上 `Authorization: Bearer <token>`。

### 步骤 4 · 上传素材(仅图片/语音/视频/文件需要)
- 纯文本、富文本、消息卡片可以直接发,不需要这步。
- 图片要先调**上传图片**接口拿到 `image_key`;语音、视频、文件要先调**上传素材**接口拿到 `file_key`。
- 发消息时把这个 key 填进 content 里,而不是直接传文件本身。

### 步骤 5 · 调用发消息接口(后端开发核心)
- 接口:`POST /open-apis/im/v1/messages`
- 关键参数:
  - `receive_id`:收件人。可以是用户的 `open_id` / `user_id`,或群的 `chat_id`。
  - `receive_id_type`:上面那个 id 是哪种类型(通过 URL query 指定)。
  - `msg_type`:消息类型(见下方接口清单)。
  - `content`:消息内容,是一段 **JSON 字符串**(注意是被转义的字符串,不是对象)。

最简单的文本消息请求体示例:
```
POST /open-apis/im/v1/messages?receive_id_type=open_id
Authorization: Bearer <tenant_access_token>
Content-Type: application/json

{
  "receive_id": "ou_xxxxxx",
  "msg_type": "text",
  "content": "{\"text\":\"今天的智驾日报已更新\"}"
}
```

## 三、接口与消息类型清单

### 用到的核心接口
| 接口 | 作用 | 用在哪一步 |
|---|---|---|
| 获取 `tenant_access_token` | 换取访问凭证 | 步骤 3 |
| 上传图片 | 拿 `image_key` | 步骤 4 |
| 上传素材(语音/视频/文件) | 拿 `file_key` | 步骤 4 |
| `POST /open-apis/im/v1/messages` | 发送消息 | 步骤 5 |
| (可选)事件订阅 / 卡片回调 | 接收用户点按钮等交互 | 卡片交互场景 |

### msg_type 消息类型对照
| msg_type | 对应内容 | 是否要先上传素材 |
|---|---|---|
| `text` | 纯文本 | 否 |
| `post` | 富文本(可混排文字、图片、链接、@人) | 图片部分需要 |
| `image` | 图片 | 是(`image_key`) |
| `audio` | 语音 | 是(`file_key`) |
| `media` | 视频 | 是(`file_key`) |
| `file` | 文件 | 是(`file_key`) |
| `interactive` | **消息卡片**(标题、图文、按钮、可交互) | 否,但内容结构最复杂 |

## 四、能力地图:这件事拆成三层,分别需要什么

### 第一层 · 平台配置与流程(偏管理/运营,不用写代码)
**要做的事**:建应用、开机器人、申请权限、走发布审核、配可见范围。
**需要的能力**:熟悉飞书开放平台后台;理解应用 / 权限 / 可见范围这套概念;能跟企业管理员协作走审批流程。
**难度**:低。偏流程和后台操作,标准/流程岗容易直接上手。

### 第二层 · 后端开发(需要学一点编程)—— 技术核心
**要做的事**:换 token 并处理缓存刷新、拼 JSON、调发消息接口、上传素材。
**需要的能力**:
- 一门后端语言(**Python 最友好**,`requests` 库即可起步)。
- 理解 **HTTP 请求**(GET/POST、请求头、请求体、状态码)。
- 理解 **JSON** 数据格式(尤其 content 是"转义后的 JSON 字符串"这个坑)。
- 理解**鉴权概念**(App ID/Secret 换 token、Bearer token、token 过期与刷新)。
- (进阶)会把脚本部署成一个能定时或被触发运行的服务。
**难度**:中。是主要的能力缺口所在,但入门门槛不高。

### 第三层 · 消息内容组织(半技术,最容易做出差异化优势)
**要做的事**:设计消息卡片(`interactive`),组织富文本排版,让通知既好看又实用。
**需要的能力**:会用飞书**卡片搭建工具**或手写卡片 JSON;有信息呈现 / 排版审美(结合资讯推送、看板经验)。
**难度**:中低。这层与既有的资讯 / 看板经验高度重合,是最容易形成个人亮点的部分。

## 五、给自己的学习清单(按优先级)

1. **搞懂两种机器人的区别**(已完成本文档即掌握)——避免学错方向。
2. **飞书开放平台实操**:亲手建一个测试应用、开机器人、申请 `im:message` 权限、走一遍发布流程。→ 补第一层。
3. **Python + requests 基础**:会发一个最简单的 POST 请求、会解析 JSON 返回。→ 补第二层地基。
4. **鉴权流程**:能独立写出"换 token → 缓存 → 发文本消息"这条最小链路。→ 第二层核心里程碑。
5. **上传素材 + 发图片/语音/视频**:跑通带素材的完整发送。→ 第二层进阶。
6. **消息卡片设计**:用卡片搭建工具做一张带按钮的通知卡片。→ 补第三层,形成亮点。
7. (进阶可选)**卡片交互回调 / 事件订阅**:让用户点按钮后能触发后端逻辑。

**建议的能力自评标注**(归档时可按此打勾):
- [ ] 第一层 · 平台配置流程
- [ ] 第二层 · Python / HTTP / JSON / 鉴权
- [ ] 第二层 · token 缓存刷新 + 发消息最小链路
- [ ] 第二层 · 素材上传与多媒体消息
- [ ] 第三层 · 消息卡片设计
- [ ] 进阶 · 卡片交互与事件回调

## 六、一句话总结

本质上就是:**一个自建应用(平台侧配置)+ 一个后端服务(管 token、拼 JSON、调接口)**,消息就能直接落到员工的飞书会话里。缺口主要在第二层的后端开发,而第一层和第三层与你现有的流程 / 资讯能力高度契合,是可以快速拿下并形成优势的部分。
